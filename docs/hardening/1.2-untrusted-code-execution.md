# Hardening 1.2 — Untrusted code execution

> **Section**: 1.2 of [HARDENING_PLAN.md](../../HARDENING_PLAN.md)
> **Priority**: 🔴 P0 / 🟠 P1
> **Status**: Specification — not implemented

## Threat model

The CLI executes code/commands from three sources that today have **no integrity check**:

1. Python plugin files dropped into `~/.system_update/plugins/`.
2. PowerShell installer fetched at runtime from `aka.ms`.
3. Strings read from a JSON cache file and passed as winget arguments.

Anyone with write access to the user's profile (or to a network share that proxies it, or to the cache file) gets code execution at the privilege level of the CLI — typically the same user, but the CLI is often run from elevated PowerShell, which makes this a privilege-relevant concern.

## Items

### 1.2.1 — Plugin loader has no sandbox or integrity check

- **File**: [src/system_update/plugins.py:281](../../src/system_update/plugins.py:281)
- **Effort**: M (½–1 day)
- **Problem**: The loader iterates `~/.system_update/plugins/*.py` and calls `importlib.util.spec_from_file_location(...)` + `spec.loader.exec_module(module)`. Any file in that directory runs at import time. There is no opt-in, no signature, no permission check on the directory.
- **Attack scenario**: Malware drops `~/.system_update/plugins/legit.py` containing arbitrary Python. Next scan → RCE in the user's session. On a multi-user machine, a low-priv attacker who can write to another user's profile (e.g., via misconfigured share) escalates when the victim runs `system-update`.
- **Proposed fix**:
  1. Default `plugins.enabled` to **`false`** in `config.py`. Loader becomes a no-op unless explicitly enabled.
  2. When enabled, validate the plugin directory before listing files:
     - Owner must be the current user.
     - Permissions must not be world-writable (Windows: check ACL excludes `Everyone`/`Users` Write; POSIX: `(stat.st_mode & 0o022) == 0`).
  3. Optional SHA-256 allowlist file at `~/.system_update/plugins/allowed.sha256`. Lines like `<sha256>  <filename>`. If present, only listed plugins load.
  4. Print a clear warning at load time: `[plugin] loading <name> (sha256=<short>) — disable with plugins.enabled=false`.
  5. Add `--no-plugins` CLI flag that bypasses the loader entirely.
- **Files to touch**:
  - `src/system_update/plugins.py` (loader gate, permission/hash checks)
  - `src/system_update/config.py` (default `plugins.enabled=False`, schema entry)
  - `src/system_update/cli.py` (`--no-plugins` flag)
  - `README.md` (document the new opt-in)
- **Tests** (`tests/test_plugins.py`):
  - Default config → loader returns empty plugin list.
  - With `plugins.enabled=true` and clean dir → plugin loads.
  - With world-writable dir → loader refuses and logs a warning.
  - With `allowed.sha256` present and plugin not in it → plugin skipped.
  - `--no-plugins` flag overrides config.
- **Acceptance criteria**:
  - [ ] Fresh install never auto-loads plugins.
  - [ ] Hostile plugin file in default location does not execute.
  - [ ] All existing plugin tests pass with `plugins.enabled=true` set in fixtures.

### 1.2.2 — Unverified PowerShell installer fetched at runtime

- **File**: [src/system_update/executors/commands.py:113](../../src/system_update/executors/commands.py:113)
- **Effort**: M (½–1 day)
- **Problem**: The PowerShell self-updater runs `iex "& { $(irm https://aka.ms/install-powershell.ps1) }"`. This fetches and executes a script over HTTPS with no hash check, no signature check, and no pinning. A compromised CDN, a TLS intercept on the user's network, or a hijacked redirect → arbitrary code at the privilege level of the running shell (frequently elevated).
- **Proposed fix** (preferred):
  1. Replace the `iex (irm ...)` invocation with `winget install --id Microsoft.PowerShell --accept-source-agreements --accept-package-agreements`. winget validates installer hashes against the manifest.
  2. If winget is unavailable, fall back to downloading the script to a temp path, comparing its SHA-256 against a hash pinned in the source (and refreshable via a documented procedure), and only then executing it.
  3. Never use `iex` on streamed remote content under any flag.
- **Files to touch**:
  - `src/system_update/executors/commands.py` (replace pwsh updater path)
  - `tests/test_executors.py` or `tests/test_checkers.py` (depending on layout)
- **Tests**:
  - Mocked winget invocation receives the right arguments.
  - Fallback path: hash mismatch aborts the install with a clear error.
  - Hash match path: script is run from the local file, not from a URL.
- **Acceptance criteria**:
  - [ ] `iex (irm ...)` no longer appears in the codebase (`grep -r "irm " src/` empty).
  - [ ] Updating PowerShell uses a verified path.

### 1.2.3 — Flag injection via tampered cache

- **File**: [src/system_update/executors/commands.py:23](../../src/system_update/executors/commands.py:23)
- **Effort**: S (≤2h)
- **Problem**: `app.latest_version` is read from `~/.system_update/cache.json` and interpolated into the winget argv as the version flag value. The cache file is plain JSON, world-readable, and writable by anyone with the user's profile access. A malicious value like `1.0 --override "& malicious.exe"` becomes a separate winget flag — flag injection. Even without code execution, an attacker can flip `--scope user` to `--scope machine` or inject `--accept-source-agreements` for unwanted sources.
- **Proposed fix**:
  1. Validate `latest_version` (and any other cache string flowing into argv) against a strict regex: `^[A-Za-z0-9.+\-_~]+$`. Reject and log otherwise.
  2. Apply the same validation to `package_id`, `package_name`, and any other field that becomes an argv token.
  3. Add a helper `_safe_argv_token(value: str, *, field: str) -> str` in `executors/commands.py` and use it everywhere argv is built from cache.
- **Files to touch**:
  - `src/system_update/executors/commands.py`
  - `src/system_update/cache.py` (optionally validate on load too)
- **Tests** (`tests/test_executors.py`):
  - Valid version strings pass through.
  - Strings containing spaces, dashes-with-leading-space, quotes, semicolons, or backticks are rejected.
  - Builder raises a clear error pointing at the offending field.
- **Acceptance criteria**:
  - [ ] No raw cache string is concatenated into argv without passing through `_safe_argv_token`.
  - [ ] Tests cover the rejection path.
