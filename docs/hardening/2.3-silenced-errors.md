# Hardening 2.3 — Silenced errors

> **Section**: 2.3 of [HARDENING_PLAN.md](../../HARDENING_PLAN.md)
> **Priority**: 🟠 P1 / 🟡 P2 / 🟢 P3
> **Status**: Specification — not implemented

## Threat model / failure mode

Several catch-all `except Exception:` clauses currently mask real failures and produce empty results that look like a clean run. This is a correctness and observability bug: a network outage, a malformed response, or a missing tool produces a "no vulnerabilities found" report identical to a real clean scan. Users cannot distinguish "we're fine" from "we couldn't tell".

## Items

### 2.3.1 — OSV scanner swallows all exceptions

- **File**: [src/system_update/security/osv.py:37](../../src/system_update/security/osv.py:37)
- **Effort**: S (≤2h)
- **Problem**:
  ```python
  try:
      data = network.fetch_json(...)
  except Exception:
      data = {}
  ```
  Any failure (timeout, 5xx, JSON decode, rate limit) becomes "no vulns". No log, no retry.
- **Proposed fix**:
  1. Replace bare `except Exception` with specific catches: `urllib.error.URLError`, `TimeoutError`, `json.JSONDecodeError`, plus `OSError` for connection-reset class errors.
  2. Log at WARNING with the exception class and the URL (URL host only — never log query strings that may contain identifiers).
  3. Add the failure to the result object as a partial-failure marker rather than an empty dict, so downstream UI can show "OSV check skipped — network error".
  4. Wire in retry+backoff (see item 4.6 / hardening 4 PR) — but since that may land separately, accept that this PR adds the **structured error**, not the retry, and the retry-add later is purely additive.
- **Files to touch**:
  - `src/system_update/security/osv.py`
  - `src/system_update/security/__init__.py` (if a result type needs a new field for `errors: list[str]`)
  - `src/system_update/ui/system.py` or wherever vuln results are rendered (show partial-failure marker)
- **Tests** (`tests/test_security.py`):
  - Network failure → `result.errors` non-empty, no exception bubbles out.
  - JSON decode error → same.
  - Successful response → no errors, populated vulns.
- **Acceptance criteria**:
  - [ ] No `except Exception` catch-all in `security/osv.py`.
  - [ ] Failure produces an audit-trail-visible signal (log + result field).

### 2.3.2 — `npm audit` runs in CWD

- **File**: [src/system_update/security/npm.py:18](../../src/system_update/security/npm.py:18)
- **Effort**: S (≤2h)
- **Problem**: `npm audit` requires a `package.json`. When the CLI is invoked from a directory without one (the usual case), npm returns a non-JSON error or stale data. The current code parses whatever comes out and silently produces nothing.
- **Proposed fix**:
  1. Detect the situation up front: if `npm root -g` succeeds, run `npm audit --prefix $(npm root -g)/..` so the audit runs against globally installed packages — which is what the rest of the scanner cares about.
  2. If neither a local `package.json` nor a usable global root is found, skip the audit cleanly and emit a one-line INFO log: `npm audit skipped: no package.json or global root reachable`.
  3. Treat npm audit's `--json` exit code 1 (vulnerabilities found) as success, exit code 2+ as failure (network/internal error).
- **Files to touch**:
  - `src/system_update/security/npm.py`
- **Tests** (`tests/test_security.py`):
  - Mock `npm audit --json` returning vulnerabilities → parsed correctly.
  - Mock `npm audit` failing with no `package.json` → result is "skipped", not "clean".
  - Global-root path used when local is missing.
- **Acceptance criteria**:
  - [ ] No misleading "clean" output when audit was actually skipped.
  - [ ] Existing happy-path tests unchanged.

### 2.3.3 — YAML config ImportError silently continues

- **File**: [src/system_update/config.py:253](../../src/system_update/config.py:253)
- **Effort**: S (≤2h)
- **Problem**: When PyYAML is not installed and the user has a `.yaml` config, the loader logs an error but proceeds with default config. The user thinks their settings are loaded; they aren't.
- **Proposed fix**:
  1. If PyYAML is missing **and** a `.yaml`/`.yml` config file exists, raise a clear error at startup: `"PyYAML is required to load <path>. Install with: uv pip install pyyaml or use a JSON config."`
  2. If only a `.json` config exists, never import yaml at all.
  3. Document the fallback behavior in `README.md`.
- **Files to touch**:
  - `src/system_update/config.py`
  - `README.md`
- **Tests** (`tests/test_config.py`):
  - YAML file present, PyYAML mock-missing → loader raises with clear message.
  - JSON file present, no YAML access → no import attempted (use `unittest.mock` to assert `yaml` not imported).
  - Both files present, prefer JSON if YAML import fails (**alternatively**: prefer YAML and raise — pick one and document in the spec PR description).
- **Acceptance criteria**:
  - [ ] User cannot silently run with default config when their YAML config was meant to load.
  - [ ] Decision documented in README.
