# Hardening 1.1 — Credentials in argv

> **Section**: 1.1 of [HARDENING_PLAN.md](../../HARDENING_PLAN.md)
> **Priority**: 🔴 P0 (critical security)
> **Status**: Specification — not implemented

## Threat model

Any string passed on a process command line on Windows is visible to **all local users** via `tasklist /v`, `Get-Process`, WMI (`Win32_Process.CommandLine`), and ETW. Even processes that exit immediately leak credentials to anyone polling fast enough or to forensic tooling. Redacting the value in our **logs** does not address this — the OS itself records the argv.

This affects two paths in the codebase: the WinRM remote-execution password and webhook bearer tokens.

## Items

### 1.1.1 — Winrs password leak

- **File**: [src/system_update/remote.py:201](../../src/system_update/remote.py:201)
- **Effort**: L (1–3 days)
- **Problem**: `winrs -r:<host> -u:<user> -p:<password> ...` puts the password directly in argv. The `build_debug_argv` helper redacts it for logs, but the actual spawned process still has the cleartext password in its command line.
- **Reproducer**:
  ```powershell
  python -m system_update --remote-host HOSTA --remote-user admin --remote-password 'Secret!' ...
  # In another shell:
  Get-CimInstance Win32_Process | Where-Object CommandLine -match 'winrs' | Select CommandLine
  ```
- **Proposed fix**:
  1. Add `pywinrm` (or `pypsrp`) to `pyproject.toml` as an optional dependency.
  2. Implement a new transport `WinRMTransport` in `remote.py` that uses HTTPS + NTLM/Kerberos via the library — the password never touches argv.
  3. Keep `winrs` as a fallback **only** when the user explicitly opts in via `--use-winrs` and pass the password via a temporary credential file or `runas /savecred`. Document the security caveat in `--help`.
  4. Update `build_debug_argv` to assert the password placeholder is never present in the final argv (defensive check).
- **Files to touch**:
  - `src/system_update/remote.py` (new transport class, dispatch logic)
  - `pyproject.toml` (optional `pywinrm` dependency, extras: `remote`)
  - `README.md` (mention HTTPS WinRM is now the default)
- **Tests** (`tests/test_remote.py`):
  - Mock `pywinrm.Session.run_cmd` and assert no password appears in any subprocess call.
  - Assert the legacy `winrs` path is only used when `--use-winrs` is passed.
  - Regression test: `build_argv()` must never contain the literal password string.
- **Acceptance criteria**:
  - [ ] Default remote run uses HTTPS WinRM with no password in argv.
  - [ ] `Get-CimInstance Win32_Process` during a run shows no cleartext password.
  - [ ] All existing remote tests pass; new tests cover password isolation.
  - [ ] Docs updated.

### 1.1.2 — Webhook bearer token leak

- **File**: [src/system_update/notifications.py:130](../../src/system_update/notifications.py:130)
- **Effort**: S (≤2h)
- **Problem**: Webhook delivery shells out to `curl -H "Authorization: Bearer <token>" ...`. Same argv-leak as 1.1.1.
- **Proposed fix**: Replace the `curl` invocation with `urllib.request.Request` (already a dependency, used in `network.py`). Pass headers via `Request(url, data=..., headers={'Authorization': f'Bearer {token}'})` and use the existing `network.fetch_*` rate-limited path if applicable.
- **Files to touch**:
  - `src/system_update/notifications.py` (replace `subprocess.run(['curl', ...])` with `urllib.request`)
  - Remove any helper that builds curl argv with the token.
- **Tests** (`tests/test_notifications.py`):
  - Mock `urllib.request.urlopen` and assert the `Authorization` header is sent.
  - Assert no `subprocess` call is made for webhook delivery.
  - Cover timeout, non-2xx response, and connection error paths.
- **Acceptance criteria**:
  - [ ] No `curl` subprocess for webhook delivery.
  - [ ] Token never appears in argv.
  - [ ] All notification tests still pass.
